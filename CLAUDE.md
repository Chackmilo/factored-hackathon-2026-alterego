This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Read `AGENTS.md` before any non-trivial change: it holds the hackathon rules (violations disqualify the work), judging metrics, verified data findings (section 7), target architecture, the gap between code and plan (section 9), and a pointer to `docs/PLAN.md` (problem question, plan, roadmap, decision log). `docs/TEAM_BRIEF_COMPLEMENTED.md` (v2.5) holds the dispute policy spec, data contracts and evaluation spec; `docs/SUPABASE_VERCEL.md` holds the identity, database and deployment design; `src/rules/dispute_policy.py` implements v2.3 (spec and traceability matrix in `docs/specs/dispute-policy-v2.3.md`, team resolutions in `docs/technical-discuss-points.md`). ## Architecture: two stacks side by side

The repo holds two decision paths. Know which one you are touching.

**Decided 26-Sep, not yet in code:** the Vercel deployment on free plans (the repo has no Vercel config) and moving `.python-version` to 3.12 (the Docker `dev` service already runs 3.12). The Supabase Auth verification and the Postgres path (`bank` read-only serving copy, `ops` for writes) decided the same day are in code, described below. Read `docs/SUPABASE_VERCEL.md` before touching auth, the gateway or deployment.

**Baseline (wired to the API and `main.py`).** `src/api/app.py` calls `HybridOrchestrator` in `src/agents/orchestrator.py`: a single-shot pipeline of `PIIMasker`, then `DeterministicRulesEngine` (`src/rules/engine.py`), then the hand-tuned `MLFraudDetector`, then a keyword branch calling always-succeeding mocks in `src/agents/tools.py`, with escalations going to the in-memory `hitl_queue`. It takes `customer_id` from the request body, is USD only and simulates LLM tokens. The team decided (26-Sep) to measure it as the reference baseline as is, with only its crash fixed: do not repair its unsafe behavior (it counts in the report), build dispute features in the dispute stack, and never deploy it (its in-memory queue cannot work on stateless Vercel functions). Its four routes (`/api/v1/sanitize`, `/triage`, `/hitl/queue`, `/hitl/resolve`) answer only when `APP_ENV` is `development` or `test` (404 otherwise, as the local issuer); the harness drives it through `src/eval/baseline_adapter.py`, not the routes.

**Dispute stack (wired to the API since 27-Sep through `src/api/dispute_routes.py`).** Customer endpoints under `/api/v1/disputes`, console endpoints under `/api/v1/console` (need `app_role == "agent"` in the token, else 403), and a local issuer under `/api/v1/auth` that only exists when `APP_ENV` is `development` or `test`. `get_orchestrator()` is an `lru_cache` singleton: with `DATABASE_URL` set it runs on Postgres (`PostgresBankingGateway` over `bank` and the `ops` views, `OpsStore` on the same database; apply `supabase/migrations/*.sql` and run `src.data.publish_serving` first), otherwise on DuckDB from `LAKEHOUSE_PATH` and `OPS_DB_PATH`. Either way it wires the `UnderstandRouter` with Jev and the daily budget, loads the risk scorer from `FRAUD_MODEL_PATH` (default `models/fraud_risk_ieee.joblib`) and seeds the team questions. Tests override it with `app.dependency_overrides`.

- `src/auth/session.py`: Supabase-shaped ES256 sessions. `SessionVerifier` checks the token against the project JWKS (`SUPABASE_URL`) or the per-process local issuer (`APP_ENV` test or development only; `LOCAL_ISSUER_ENABLED=true` with `APP_ENV=production` raises when `src/api/app.py` is imported, so the app refuses to start), requires `aud = authenticated` and the matching `iss`, and reads `customer_id` and `app_role` from `app_metadata`. `create_test_session` mints local tokens; `get_current_session` yields a `VerifiedSession` (403 when a customer token carries no `customer_id`); `require_agent` guards the console; `actor_id` is the audit identity. HS256 and `alg: none` get 401. Gateway tools take this session, never a raw `customer_id`.
- `src/rules/dispute_policy.py`: `DisputePolicyEngine.evaluate` checks the v2.3 clauses in a fixed order and returns on the first match: regulator or legal keywords `POL-ESC-LEGAL` (before the window), charge identification `POL-CLARIFY` (zero or several candidates, Jev intent confidence under 0.70, stolen-card probability in [0.40, 0.60]; a third round is `POL-ESC-AMBIG`), disputable charge `POL-DISP-TYPE` (Approved Purchase, Payment, Withdrawal or Transfer; future-dated charges and a decisive out-of-scope intent abstain; a null `amount_usd` escalates), window `POL-WIN-60`, then the escalations `POL-ESC-500`, `POL-ESC-ML-RISK`, `POL-ESC-MULTI`, `POL-ESC-DISTRESS` (the first decides, the others land in `secondary_clauses`), then the candidate flag `POL-AUT-150` and plain intake `POL-AUT-INTAKE`. `POL-AUT-LOCK` (stolen-card claim or multi-charge fraud) is attached to any outcome as `card_lock_recommended`; `ACTION_AUTH_MATRIX` declares the authentication each action needs. Reordering changes outcomes. The window counts from the bank process day: pass `transaction_date` as the raw UTC timestamp (it is shifted 6 h back) or as a `date` already equal to `process_date`. The charge fields are optional only for the clarification path; past it, a missing charge raises `ValueError`. Jev signals and the case memory are `Optional` typed inputs: `None` means keyword fallback (distress, stolen card) or no check (intent confidence). Customer-facing text is `explanation_es` / `explanation_pt`, templated from the decision; it never mentions credit or promises a lock. `message_escalation` names `POL-ESC-LEGAL` or `POL-ESC-DISTRESS` when the message and the case memory alone fire it, before any charge is known: the guard of the policy explainer's routing.
- `src/orchestrator/dispute_orchestrator.py`: `DisputeOrchestrator.handle_message` runs Understand (the router below, or the keyword extractor alone when built without one, as in the test fixtures and the eval harness) -> candidate matching over the session customer's own charges -> `DisputePolicyEngine` -> Act (cases, handoffs and locks in the ops store; the card lock through the gateway only after the customer's yes) -> Verify (read back before replying) -> Escalate (`StructuredHandoffPacket`). Conversation state lives in the ops store: `new`, `awaiting_clarification`, `awaiting_lock_confirmation`, `closed`, `escalated`. A charge with an open case is not opened twice. A message that names several charges at once counts them: three or more named without ambiguity join the 48-hour count, so `POL-ESC-MULTI` sends the turn to a human with the `MULTI_CHARGE_FRAUD` lock offer and opens no case (the turn is decided on the first disputable one, and the handoff lists every named charge); otherwise every charge that matches one of the amounts is listed, and the reply that opens the picked case reminds the customer of the others. A clarification that carries a lock recommendation (a lost or stolen card) offers the lock first and asks the clarification again after the answer, with the same listed charges. A first message with no dispute signal, a loss report with no hint, or a reply that names no charge after a list of recent charges (`NO_CANDIDATE_CHARGE`) never picks the customer's only charge. The lock needs the customer's own yes: an answer to the lock question locks only when every word says yes (a closed vocabulary, as for option replies: "sí", "dale", "sim, pode bloquear", "no hay problema, bloquéala"), refuses only with refusing words read without the dispute phrases (a bare no, "no gracias", "mejor no", "no quiero" on its own, a negated lock verb such as "no la bloqueen"), and anything else (a question, a doubt, a request to wait, "no importa", a want with its reason such as "no quiero que la usen", a refusal next to a lock verb or a bare "sí", an emoji, "no reconozco un cargo") is asked again. When a bank read fails before the policy runs (`SystemOfRecordUnavailableError`, `TimeoutError`, `ConnectionError`), the turn goes to a human with `SYSTEM_OF_RECORD_UNAVAILABLE` and confirms nothing; so does a failure while listing the deferred charges again, once the lock answer is applied. A lock that fails or times out after the yes always gets its own `ACTION_VERIFICATION_FAILED` handoff and the pending-lock reply; a card list that fails only drops the lock offer (TQ-028). The `LOCK_CARD` audit row records the reason code of the offered lock. Built with an `explainer` (see `src/rag/`), a turn in state `new` whose `policy_question` is set, and that fires neither `message_escalation` nor Jev's stolen-card band (0.40 or more) or out-of-scope intent, goes to the policy explainer instead of the dispute turn: outcome `POLICY_EXPLANATION` (or `SAFE_POLICY_ABSTENTION` when it abstains), the state stays `new`, no case is opened, the bank is not read, and the audit row is `POLICY_EXPLAINED`.
- `src/understand/`: `UnderstandRouter` (`router.py`) picks the signals engine for each turn. Jev (`jev_extractor.py`, `typesafe-sdk`, model pinned to `jev-1.13.0`) runs when `TYPESAFE_API_KEY` is set and the daily cap allows (`src/llm/budget.py`: `LLM_DAILY_BUDGET_USD`, default 2 USD a day across providers, usage rows in `ops_llm_usage`). The ES/PT keyword and regex extractor (`keyword_extractor.py`) takes trivial turns (12 characters or fewer, the lock confirmation, or an option reply in `awaiting_clarification`), turns without a key or budget, and any Jev failure. Jev sees only the masked message; amounts, dates, yes/no and option numbers always come from the keyword extractor on the raw text. `amount_hints` holds every charge amount of a message (each one with a currency, and the unit-less amounts of a list that ends in one, such as "45, 80 y 120 dólares"; never a date or a balance), while `amount_hint` keeps the first-amount reading. An option reply is one digit from 1 to 9 among words of a closed ES/PT vocabulary (`option_reply`); when a loss or theft is told, the charge date comes only from the clauses that tell a charge and no loss (a date on its own joins the clause after it when a comma follows, else the sentence before it); a clause that names one charge (a charge word, a disputable type such as pago or retiro, a statement line such as movimiento or lançamento, or an amount in a currency that is not a balance) and disputes it ("no reconozco", "no hice", "no es mío", "não é meu" and the like) wins over a mention of the statement, never over a loan or another product. `policy_question` marks a question (a question mark or an opening question word) about the dispute rules (deadlines, process, what can be disputed, refunds, unlocking) that names no charge of its own: no amount, date, demonstrative ("este cargo"), dispute phrase, disputed clause, stolen card or other product. It is a signal, not an intent, so it changes nothing while the explainer is off, and it errs towards no. Replies are always the policy templates: with `ANTHROPIC_API_KEY` set the router only records a Claude choice, since no Claude call exists yet.
- `src/rag/`: the policy explainer of `docs/RAG_IMPLEMENTATION_ROADMAP.md`. `get_orchestrator` builds it with `load_policy_explainer(RAG_GATE_PATH)` (default `data/rag_gate.json`: `{"retriever": "bm25", "tau_upper": ..., "tau_lower": ...}`); the file does not exist until Task 4.1 calibrates the thresholds, so the explainer is off and every turn takes the dispute flow. `load_corpus` reads `data/policy_corpus.json` (the 13 clauses of spec v2.3 with the exposure of TQ-037: internal clauses have no answer and share one fixed redirect without a clause id) and refuses an unknown exposure or a readable clause without both answers. `BM25Retriever` indexes `Clause.index_text` (official Spanish text plus ES and PT keywords, the text E5 will index too); `ConfidenceGate` needs both thresholds, which come only from the development split of policy questions (Task 4.1); `PolicyExplainer.explain` takes the masked message and returns `answer` (the clause template plus `[POL-XXX]`), `redirect`, `clarify` (public titles only) or `abstain`, with the top hits for the audit log. Readers of the corpus open it with `encoding="utf-8"`.
- `src/ops/store.py`: `OpsStore` on a DuckDB file (default `data/ops.duckdb`, `":memory:"` in tests) or on Postgres when given a `postgresql://` URL (`OpsStore.apply_postgres_migration` applies every file in `supabase/migrations/` in name order). Tables: conversations, messages, dispute_cases, card_locks, handoffs, team_questions, audit_log (append-only), plus llm_usage (created by `LlmBudget`). Write its SQL against `ops_<table>` names with `?` placeholders: on Postgres the store rewrites them to `ops.<table>` and `%s`, so a new table needs an entry in `OPS_TABLES` and a migration. `case_memory()` aggregates the customer's prior handoffs, cases and lock refusals for the policy.
- `src/tools/gateway.py`: `BankingToolGateway` act-and-verify tools on the DuckDB lakehouse. Each mutation checks ownership against the silver tables (`UnauthorizedAccessError`), writes, then reads back (`ActionVerificationError` when the read-back disagrees, and also when the product does not exist; `RecordNotFoundError` is raised only by `get_customer_profile`). `execute_lock_card` takes a `reason_code` (`STOLEN_CARD_CLAIM` or `MULTI_CHARGE_FRAUD`, the `CHECK` on `ops.card_locks.reason`) and rejects any other with `ValueError` before writing. Merchant names leave the gateway wrapped in `<untrusted_merchant_data>` tags as the prompt-injection boundary. `PostgresBankingGateway` (`gateway_postgres.py`) has the same interface over `bank.*` and the live `ops` views and functions of `0003_bank.sql` (`ops.v_product_status`, `ops.v_customer_policy_facts`, `ops.business_today()`); its card lock writes `ops.card_locks`, never `bank`. On both backends the orchestrator opens cases in the ops store; the gateways have no case tool. Both return None for SQL NULL (the DuckDB gateway maps the NaN and NaT that pandas reads) and raise `SystemOfRecordUnavailableError` when the database cannot be reached: a DuckDB file locked by another process, or a Postgres that refuses, drops or times out (5-second connect timeout).
- `src/domain/handoff.py`: `StructuredHandoffPacket`, the HITL handoff contract.
- `src/data/`: DuckDB lakehouse at `data/lakehouse.duckdb`. `ingestion.py` reads CSVs straight from S3 into `bronze_*`, deduplicates on composite business keys into `silver_*` (transaction duplicates land in `quarantine_duplicate_transactions`), and builds `gold_transactions` (`amount_usd` fixed at silver with `amount_usd_source`, window flags) and `gold_customers` (account age, complaints in the last 90 days). The default `sample_only=True` loads the first 25k rows of `customers.csv` (the file is in random order, so the sample matches the full country and segment mix) plus only their products, 2026 complaints and June 2026 transactions. `sample_only=False` loads all customers and every year of transactions (2023 to 2026, about 800 MB from S3); the team keeps that load in `data/lakehouse_full.duckdb`. Only `data/` is ingested; `data_backup_20260831/` is a different generation of the data (AGENTS.md section 7). `publish_serving.py` copies a minimized subset (no `is_fraud`, `fraud_score` or PII columns) into the Postgres `bank` schema and checks parity; it never touches `ops`.
- `src/eval/`: the evaluation harness. It runs the JSONL cases through the proposed stack in rules-only mode (keyword extractor, no model, no LLM, on a bank fixture built per case) and through the baseline via `baseline_adapter.py`. Suites: `data/eval/dev_cases.jsonl` (18 team-generated development cases) and `data/eval/heldout_cases.jsonl` (250 held-out cases built by `heldout.py`, frozen 30-Sep with its SHA-256; design labels until the team's labels replace them). A case may carry an `attack` (run through the FastAPI app with forged, expired or missing tokens, or another customer's conversation), a `fault` (one ops store or gateway method returns nothing, fails its read-back or times out) and `accepted_outcomes`; the judge adds `unauthorized_access`, `false_confirmation` and `unauthorized_disclosure`. `labeling.py` exports the four labeling sheets and computes Cohen's kappa. `rag_benchmark.py` measures the policy explainer on the team's bank of policy questions (`data/eval/policy_questions_dev.jsonl` and `_test.jsonl`, Task 1.2: `question_id`, `language`, `text`, `expected_action` answer, clarify or abstain, `expected_clause_ids`, `provenance`), calibrates the gate on the development split only, measures the test split once (refused if it no longer matches its `.sha256`), and with `--write-gate` writes the gate file that turns the explainer on.

## Gotchas

- **"Today" is 2026-06-17**, the dataset end date. Window and account-age math uses it, not the wall clock. It is hardcoded in many places, SQL included (`ops.business_today()` in `0003_bank.sql`): search `src/` and `supabase/` for `2026-06-17` and `date(2026, 6, 17)` and change every copy together. Two copies mislead: `ingestion.py` redefines `ANCHOR_DATE` locally in the gold-layer block (the copy gold SQL actually uses), and in the app the orchestrator's `today` becomes the policy's `current_date`, so the `DisputePolicyInput` default only reaches direct callers such as the policy tests.
- **Event time is offset.** Each daily partition spans 06:00 to 05:59 of the next day, so `process_date` = date(`transaction_date` - 6 h). `CAST(transaction_date AS DATE)` misdates about 24% of rows and gives 227 sampled charges a day count of -1. Use `process_date` for window and velocity math (AGENTS.md section 7).
- **`fraud_score` leaks `is_fraud`** (every non-fraud row scores <= 30) and `is_fraud` itself is random (discussion doc sections 5 and 6), so the served risk score comes from a model trained on the IEEE-CIS competition (`src/ml/fraud_risk_transfer.py`, spec `docs/specs/fraud-risk-model-v1-ieee-cis.md`) on the 19 deployable contract features; `POL-ESC-ML-RISK` reads its threshold from the bundle (percentile 98 of the Web and App window), not the 0.70 constant. `fraud_score` stays in `gold_transactions` for analysis only; models and the baseline use it nowhere. The `fraud_score` fields in `src/domain/schemas.py`, `src/hitl/queue.py` and the orchestrator are a name collision: they carry `MLFraudDetector.fraud_probability`, not the dataset column. Without the model file (git-ignored; training needs the IEEE-CIS files in `data/kaggle`), `get_orchestrator` loads no scorer, `ml_risk_score` stays 0.0 and `POL-ESC-ML-RISK` never fires.
- **The DuckDB gateway reads `gold_*` and writes the card lock to `silver_products`.** Gold tables are materialized snapshots that stay stale until ingestion reruns, so the orchestrator adds the ops store's own cases to `complaints_last_90d` itself, with the rule of `ops.v_customer_policy_facts` (created on or after the business day minus 90). Ops rows carry wall-clock timestamps, so every case the running app opens counts. `PostgresBankingGateway` reads live views over `bank` plus `ops` instead (`docs/SUPABASE_VERCEL.md` section 4.5) and flags it with `complaints_include_ops_cases`.
- Gateway and orchestrator tests run against team-generated fixtures, never the real lakehouse: `fixture_db` in `tests/test_dispute_flow.py` and `bank_fixture_db` plus `ops_store`, `orchestrator`, `owner_session` in `tests/conftest.py` (two customers, two cards, eight charges). `tests/test_dispute_api.py` overrides `get_orchestrator` to use them. Jev in tests is `StubJev` or `JevExtractor` with a fake client; no test calls the real Jev.
- `tests/test_data_integrity.py` is the one suite that reads the real `data/lakehouse.duckdb`, and it skips silently when the file is missing (CI and the `dev` service's default command deselect it). A green run without the lakehouse has not checked the data.
- **Docker `dev` service** (compose profile `dev`, with the `db` Postgres): it bind-mounts the repo at `/app` and keeps its virtualenv in the image at `/opt/venv`, so it never touches a host `.venv`; rebuild it (`docker compose build dev`) after `uv.lock` changes. It reads the host `.env` as a local run does. Use it wherever the host Python fails: on 29-Sep Windows Application Control blocked the duckdb, pandas and scikit-learn DLLs of a host `.venv`.
- **Text files are UTF-8; say so.** `read_text()` or `open()` without `encoding="utf-8"` uses the platform default, cp1252 on Windows, which turns "México" into "MÃ©xico" and breaks the Portuguese markers without raising. `tests/test_text_encoding.py` runs the current readers with `-X warn_default_encoding`; CI (Linux) cannot see the bug otherwise.
- `data/lakehouse.duckdb` is a relative path, so run commands from the repo root. It is git-ignored; rebuild it with the ingestion command.
- `.env.example` omits the AWS keys (they come from the data dictionary PDF). Without them `get_db_connection` in `src/data/db.py` silently skips the S3 setup, so ingestion fails later at the first S3 read, not at connect. `S3_BUCKET_NAME` and `AWS_DEFAULT_REGION` have working defaults. It also omits `TYPESAFE_API_KEY`, `LLM_DAILY_BUDGET_USD` and `FRAUD_MODEL_PATH`. `src/core/config.py` and `src/data/db.py` call `load_dotenv()` at import, so a `TYPESAFE_API_KEY` in `.env` turns on real, billed Jev calls in the local API.
- The local issuer signs with an ES256 key generated per process: each `--reload` restart invalidates the tokens minted before it (401 `Invalid session token.`), so mint a fresh one.
- DuckDB allows one writer process. An open notebook kernel or other process holding `data/lakehouse.duckdb` makes ingestion fail with "Cannot open file ... being used by another process"; the gateway turns the same error into `SystemOfRecordUnavailableError`, so every chat turn that reads the bank goes to a human until the file is free.
- Thresholds live in two places: the dispute policy hardcodes its own in `dispute_policy.py` (except the ML-risk threshold, which the orchestrator takes from the scorer's `policy_threshold`); the env thresholds in `src/core/config.py` (`MAX_AUTONOMOUS_TRANSACTION_LIMIT` and friends) feed only the baseline.
- `POL-AUT-150` is a candidate flag (`provisional_credit_candidate`) a human approves in the HITL console (rule 8; decided 26-Sep, in code since 27-Sep). The action stays `OPEN_DISPUTE_ONLY` and the customer hears that the case is registered and under review.
- **The held-out suite is frozen.** Never edit its cases or tune a threshold on its results: fix a system bug it reveals with a test of its own, and let the adjudicated human labels (`data/eval/labeling/README.md`) replace the design labels as a new version with a new SHA-256. `.gitattributes` keeps it LF so the hash holds on Windows.
- Open questions for the team go in `data/fixtures/team_questions.json` as the next `TQ-NNN` (commits and docs cite these ids). `get_orchestrator()` seeds missing ids into the console's Questions tab and applies answers recorded in the file, never overwriting an answered question.
