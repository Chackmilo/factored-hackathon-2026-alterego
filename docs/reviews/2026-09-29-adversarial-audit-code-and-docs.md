**Findings below that do not appear anywhere in audit v3's 31 items, spot-checked directly (not through a subagent) against the code on this branch and confirmed real:**

- **`orchestrator-1` (Bloqueante): the lock-confirmation parser locks the card on an explicit refusal.** Confirmed by reading `src/understand/keyword_extractor.py:44-45,151-160` and `src/orchestrator/dispute_orchestrator.py:374-376` directly. `YES_WORDS` contains the bare verbs `bloquear`, `pode`, `quero` and `confirmo` with no requirement that they stand alone; when a message matches both a yes word and a no word, `_yes_no` resolves the tie by whichever match sits later in the string. `"No quiero bloquear la tarjeta"` matches `no` and `no quiero` (early) and `bloquear` (later), so it resolves to yes; `"Não quero"` and `"Não, isso não pode ser"` resolve the same way through `quero` and `pode`. The orchestrator then runs `execute_lock_card` on `u.said_yes and not u.said_no`, so an explicit refusal in Portuguese, the language rule 3 requires the demo to show, blocks the card. This is the single highest-priority item in this whole document: it is a confirmed, reproducible, unauthorized action against the customer's stated wish, in the exact language the demo must show working.
- **`gateway-1` (Alta): a stolen-card lock can land on a card that has nothing to do with the disputed charge.** Confirmed by reading `src/orchestrator/dispute_orchestrator.py:344-348` directly. `_offer_lock` takes the disputed charge's `product_id`; when that product is not one of the customer's active cards (a savings account, a loan, an investment, per the finder's count: 66% of sampled charges), it silently substitutes `cards[0]`, the first card by `product_id` order, with no relationship to the disputed charge. The customer's `yes` then locks that unrelated card, identified to them only by its last four digits.

#### `auth-3` (Alta) APP_ENV defaults to development: a deploy that forgets the variable ships the open issuer; Dockerfile and compose hardcode it

**Kind:** security_flaw &nbsp;**Perspective:** Ops &nbsp;**Owner front:** Daniel &nbsp;**Reopens decision:** ninguna

Both _app_env() in src/auth/session.py and Settings.app_env default to 'development', which enables the local issuer and the /api/v1/auth/personas and /test-session endpoints. The safe state therefore requires an explicit APP_ENV=production on every deployment; nothing in the repo sets it (no vercel.json, no api/ entry, git ls-files shows no Vercel config), while Dockerfile line 20 bakes APP_ENV=development into the image, docker-compose.yml line 14 repeats it and .env.example ships LOCAL_ISSUER_ENABLED=true. Any value other than 'production' (for example 'staging' or 'prod') also keeps the verifier accepting local-issuer tokens: probe showed APP_ENV=staging gives local_issuer_enabled() True and decodes a local token. Combined with the previous finding, a deployment with the wrong or missing APP_ENV hands the console and every customer identity to anyone with the URL. The GitHub Action tests only APP_ENV=test.
